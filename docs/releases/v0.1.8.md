# DSH Box 0.1.8

**简体中文** · [English](#english)

---

## 简体中文

这个版本把「容器里的状态」变成了可以搬的东西，让依赖图说真话，并把容器的创建从三分钟压到十秒。

### 容器资源：提取、注入、编辑

容器里那些不属于代码的状态——聊天记录、provider 密钥、插件自己的数据——现在都建模成 **kind**（位置、是否机密、独立条目的深度），可以在容器和 Box 资源库之间搬动：

- **提取**一份副本进资源库（可单独取一个会话、也可打包成 tar），**注入**回任意容器（默认拒绝覆盖，需要时逐条合并，机密文件进出都是 `0600`，运行中的容器要显式允许重启）。
- **副本有名字**，再取一份是新增（`hello` → `hello-2`）而不是覆盖已有那份。
- **一个 kind 可以跨文件。** provider 密钥是 `.credentials.yaml` 里的一个 ref，而声明「哪个环境变量持有它」的路由在 `settings.yaml` 的 `llm-pi-ai` 段——所以 `credentials` 同时带这两半，密钥是带着使用它的 provider 一起到达的（这正是之前「注入完模型列表还是只有一个」的原因）。
- **任意 YAML 片段可以按 key 路径编辑**：界面里文档是一棵树，点一个节点就编辑那一段，路径不存在就是新增那一段；CLI 里是 `resource read` / `resource write`。
- 类型来源有三处：内置（`sessions`、`credentials`）、插件在 `dshbox.resources` 里的声明、以及插件代码里拼出来的路径（作为候选，由你确认）。

### 面向 agent 的 CLI

- `dshbox apply -f <file>`：一份文档（`container:`、`types:`、`copies:`）就让资源层与之一致。幂等、支持 `--dry-run`，未知 key 直接报错而不是静默忽略。
- 所有会汇报结果的动词都支持 `--json`；`dshbox container resource read <id> <path> --section a.b` 把容器文件作为 key 路径树交给 agent。
- `dshbox help` / `container resource help` / `apply help` 不需要看界面就能说明每个动词。

### 插件依赖图

- **默认就是分层折叠**：一层装不下一个层带（超过 18 个节点）就默认收成一个汇总节点——175 个节点的容器打开是 31 个盒子，点汇总节点或层带标签即可展开。
- **红色虚线只表示真的环**（同一上下文内），跨层但无环的边是安静的灰色虚线并配图例说明；把半身分开后跨层线归零。
- **不再对能正常运行的容器报警**：启动器（`apps/cli`）现在作为 `dsh (launcher)` 节点参与，`profileContext` 不再显示「缺失」；发布包同时有 `lib/client.js` 和 `lib/client/` 时不再把浏览器半身的 `inject` 算到宿主头上（那会让它凭空多出 8 条需求、并误报「提供者未激活」）；在不同上下文各注册一次的服务名不再算冲突。
- 插件列表也变了：**它就是「已安装」的镜像**。boxfile 装过的插件会自己出现并标注「自动收录」，资源库不再需要手动导入。

### 更快的容器

拉取一个 Harness 版本时会顺带构建好客户端产物（native 插件、宿主/客户端库、Web 前端），因此创建容器只是复制 + 从 pnpm store 链接依赖：实测 **~10 秒**（此前每次都要重新构建前端，约 195 秒）。旧 base 会在第一次用它构建模板时原地补齐，旧模板则在创建容器时重建并在任务日志里说明。

### 桌面不再被 daemon 拖住

所有访问 daemon、文件系统或外部进程的 Tauri 命令都不再跑在主线程上，每个 RPC 都有超时；任务日志也补齐了每一步的耗时，并且每一行只写一次。

### 修掉两个会致命的

- **容器里 agent 一次工具都用不了。** 宿主原本从源码入口启动，同一份 Harness 包因此被加载两遍（`src` 与 `lib` 各一份，两遍各自造自己的 `Symbol`），调度器存进一份、从另一份取，于是每次工具调用都在 1 毫秒后死掉——界面只表现为「已中断 1 秒」。现在宿主启动 `apps/cli` 自己声明的构建产物入口，进程里只有一个模块世界。
- **0.1.7 上 API Key 不生效。** provider 路由从 `settings.yaml` 的 `llm-pi-ai` 段搬到了 `profiles/<profile>/cordis.patch.yml` 的层项里（旧文件被归档成 `settings.yaml.imported`）。资源类型现在按 Harness 版本选择插槽，副本注入时按**目标容器**重新解析，所以跨版本搬运依旧落在对的地方。

### 安装

| Linux (x64) | `dshbox_0.1.8_amd64.deb`、`dshbox-0.1.8-1.x86_64.rpm` |

### 测试范围

- **Linux x64：完整测试过。** 本版本在 Linux 上实际跑过：创建并启动容器、提取/注入/编辑资源、依赖图、CLI（`apply`、`resource read/write`）、界面在浏览器里逐项核对，另外 `cargo test --workspace`（43 个测试二进制）与 `pnpm build` 全绿。
- **Windows x64 与 macOS arm64：只验证了构建，没有实际运行。** CI 在这两个平台上的 runner 用与本地相同的打包脚本产出安装包（本次发布的 dry run 三平台全部成功），但**没有人启动过这两个平台的安装包来跑一遍应用**。它们能否正常启动、容器的准备与运行是否如预期，目前没有验证过。在这两个平台上遇到问题请提 issue，附上 `~/.dsh-box/logs/` 与运行目录下 `logs/daemon/` 的日志。

完整变更列表见仓库根目录的 [`CHANGELOG.md`](https://github.com/Nexus-Aethra/DSHBox/blob/main/CHANGELOG.md)。

## English

This release makes the state inside a container something you can move, makes the
dependency graph tell the truth, and takes container creation from three minutes
to ten seconds.

### Container resources: extract, inject, edit

The state a container keeps that is not code — conversations, provider keys, a
plugin's own data — is modelled as a **kind** (where it lives, whether it is
secret, how deep its entries sit) and can be moved between containers and the Box
store:

- **Extract** a copy into the store (one conversation, or the whole thing packed
  as a tarball) and **inject** it back into any container — refusing to overwrite
  by default, merging entry by entry when asked, with secret files at `0600` in
  both directions and a running container only when a restart is allowed.
- **A copy has a name**, and taking another adds one (`hello` → `hello-2`)
  instead of replacing the copy that is already there.
- **A kind can span files.** A provider key is a ref in `.credentials.yaml`,
  while the route naming the environment variable that holds it lives in the
  `llm-pi-ai` section of `settings.yaml` — so `credentials` carries both halves,
  and a key now arrives *with* the provider that uses it. (That is why injecting
  the key alone used to leave the model list at one entry.)
- **Any YAML block is editable by key path**: in the UI the document is a tree,
  picking a node loads that block, and a path that does not exist yet is how a
  block is added; on the CLI it is `resource read` / `resource write`.
- Kinds come from three places: built in (`sessions`, `credentials`), declared by
  a plugin in `dshbox.resources`, or read out of the paths a plugin's shipped
  code composes — as candidates you confirm, never as trusted paths.

### An agent surface in the CLI

- `dshbox apply -f <file>` takes one document (`container:`, `types:`,
  `copies:`) and makes the resource layer match it — idempotent, `--dry-run`
  changes nothing, and an unknown key is an error rather than a silent no-op.
- Every reporting verb answers `--json`, and `dshbox container resource read
  <id> <path> --section a.b` hands an agent a container file as a tree of key
  paths.
- `dshbox help`, `container resource help` and `apply help` describe every verb
  without the UI.

### Plugin dependency graph

- **It opens with the wide depths folded**: a depth too big for one band (more
  than 18 nodes) becomes one summary box — a 175-node container reads as 31
  boxes — and a click on the summary or the band label brings it back.
- **Red dashed means a real cycle** (inside one context). An edge the drawing
  merely cannot lay out forwards is a quiet grey dash with a legend line, and
  splitting the halves leaves zero of them.
- **It no longer cries wolf on a container that runs.** The launcher
  (`apps/cli`) is now a provider node (`dsh (launcher)`), so `profileContext` is
  not "missing"; a published package shipping both `lib/client.js` and
  `lib/client/` no longer has its browser half's `inject` list attributed to the
  host (which invented 8 requirements and reported an inactive provider); and a
  service registered once per context is not a conflict.
- The plugin list changed too: **it mirrors what is installed.** A plugin a
  boxfile installed appears on its own, marked auto-indexed, and the repository
  no longer needs manual imports.

### Faster containers

Pulling a Harness version now also builds the client artifacts (native addon,
host and client libraries, web frontend), so creating a container is a copy plus
store links: **~10s** measured, where building the frontend at container creation
took ~195s. An older base is repaired in place the first time a template is built
from it, and an older template is rebuilt at container creation — the task log
says which path was taken.

### The desktop no longer waits on the daemon

Every Tauri command that reaches the daemon, the filesystem or another process
runs off the main thread, each RPC is bounded by a timeout, and every step of a
long task now logs what it did and how long it took — once, not twice.

### Two fatal faults fixed

- **No agent could run a single tool inside a Container.** The host started from
  the source entry, which loaded one Harness package twice — once from `src`,
  once from `lib`, each creating its own `Symbol` — so the scheduler was stored
  under one and looked up under the other. Every tool call died about a
  millisecond later, and the UI showed it as a one-second interruption. The host
  now starts the built entry `apps/cli` itself declares, so the process has one
  module world.
- **API keys stopped working on 0.1.7.** The provider route moved out of the
  `llm-pi-ai` section of `settings.yaml` into a layer item of
  `profiles/<profile>/cordis.patch.yml` (the old file is archived as
  `settings.yaml.imported`). A resource type now picks its slot by Harness
  version, and a copy re-resolves against the **destination** container, so
  carrying state across versions still lands in the right place.

> **The installers on this page were rebuilt.** In the first 0.1.8 build the
> **resource page was broken in the desktop app**: the daemon, the CLI and the
> browser dev bridge all worked, but the desktop shell had registered none of
> those commands, so the UI only reported `Command list_resource_type not
> found`. The artifacts here were rebuilt from the fixed commit and uploaded
> over the originals; the version is still 0.1.8, so installing again replaces

### Testing status

- **Linux x64: tested end to end.** This release was exercised on Linux —
  containers created and started, resources extracted, injected and edited, the
  dependency graph, the CLI (`apply`, `resource read/write`), and the UI checked
  item by item in a browser — with `cargo test --workspace` (43 test binaries) and
  `pnpm build` green.
- **Windows x64 and macOS arm64: built, not run.** CI produced their installers
  on those runners with the same bundle scripts a developer runs locally (all
  three platforms passed in this release's dry run), but **nobody has launched
  these installers and used the app on either platform**. Whether they start, and
  whether container preparation behaves there, is unverified. Please open an
  issue with `~/.dsh-box/logs/` and `logs/daemon/` from the runtime directory if
  something goes wrong.
